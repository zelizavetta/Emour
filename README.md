# Emour

Дневник самонаблюдения: настроение, энергия, тревога, симптомы, заметки и расписание приёма лекарств. Проект включает мобильное приложение, отдельный веб-клиент, HTTP API и общий TypeScript-пакет.

> **Перед первым запуском:** в репозитории нет базовой схемы PostgreSQL. Сборка приложений возможна без неё, но операции с данными требуют заранее подготовленной БД. Подробности — в разделе [База данных](#база-данных).

## Возможности

| Возможность | Мобильное приложение | Веб-клиент |
| --- | --- | --- |
| Вход по email и паролю | Да | Да |
| Оценки настроения, энергии и тревоги по шкале 1–5 | Да | Да |
| Запись симптомов | Да | Да |
| Календарь и просмотр записей дня | Да | Да |
| Графики за 7, 30 и 90 дней | Да | Нет |
| Заметки с эмоцией и датой | Создание, чтение, изменение, удаление | Создание и чтение |
| Лекарства: дозировка, время и дни приёма, включение и удаление | Да | Да |
| Локальные напоминания о лекарствах и отметки приёма | Да | Нет |

Предусмотрены две серверные роли:

- `owner` — чтение и изменение данных;
- `viewer` — только чтение. В мобильном интерфейсе доступна только статистика; веб-интерфейс не скрывает действия записи, но сервер их отклоняет.

Это **общий дневник**, а не многопользовательский сервис с отдельными данными каждого аккаунта: запросы не разделяют записи по пользователям. Самостоятельной регистрации на сервере нет; учётные данные задаются окружением.

Полноценный офлайн-режим и очередь синхронизации не реализованы. Записи загружаются через API. Уже запланированные мобильные уведомления выполняются локально; идентификаторы уведомлений и отметки приёма хранятся на устройстве.

Приложения обращаются к Express API, API — к PostgreSQL. `@emour/core` используется всеми приложениями. Это репозиторий с несколькими npm-пакетами, **без npm workspaces**: зависимости устанавливаются отдельно.

## Требования

- Node.js **не ниже 20.19.4** — это минимальная версия, указанная зависимостями React Native/Metro в lock-файле. Рекомендуется актуальная поддерживаемая LTS-версия.
- npm и Git.
- PostgreSQL и `psql` для работы с БД и ручного применения SQL. Версия PostgreSQL проектом не зафиксирована.
- Для нативного Android: Android Studio, Android SDK, JDK 17, настроенные `JAVA_HOME`/Android SDK и эмулятор либо устройство с USB debugging. Для USB-команд нужен `adb` в `PATH`.
- Для локальной iOS-сборки: macOS, Xcode и CocoaPods. Windows не поддерживает локальную сборку iOS.
- Для EAS-сборок: доступ к EAS CLI; облачные сборки требуют настройки Expo/EAS.

Зависимости приложений зафиксированы их `package-lock.json`. Корневой `npm install` не устанавливает зависимости вложенных пакетов.

## Установка

Все команды ниже выполняются **из корня репозитория**, если явно не указан другой каталог.

### 1. Собрать и упаковать общий пакет

```sh
npm ci --prefix packages/core
npm run build:core
```

Результат: `packages/core/dist/` и `packages/core/emour-core-1.0.0.tgz`.

### 2. Установить зависимости приложений

```sh
npm ci --prefix apps/backend
npm ci --prefix apps/mobile
npm ci --prefix apps/web
```

Можно установить только нужные приложения. **Порядок важен:** каждое приложение зависит от локального архива core, которого нет в чистом клоне до выполнения первого шага.

### 3. Подготовить окружение

Скопируйте шаблоны, не перезаписывая уже настроенные `.env`.

PowerShell:

```powershell
Copy-Item apps/backend/.env.example apps/backend/.env
Copy-Item apps/mobile/.env.example apps/mobile/.env
```

Bash:

```sh
cp apps/backend/.env.example apps/backend/.env
cp apps/mobile/.env.example apps/mobile/.env
```

Заполните значения по следующему разделу и подготовьте БД. Для стандартного локального запуска веб-клиента `.env` не нужен.

## Настройка окружения

### Backend: `apps/backend/.env`

Пример для локальной разработки; замените учётные данные и секрет:

```dotenv
DATABASE_URL=postgresql://emour:replace-me@localhost:5432/emour
JWT_SECRET=replace-with-a-long-random-secret
APP_EMAIL=owner@example.com
APP_PASSWORD=replace-owner-password
VIEWER_EMAIL=viewer@example.com
VIEWER_PASSWORD=replace-viewer-password
CORS_ORIGIN=http://localhost:5173
```

| Переменная | Назначение |
| --- | --- |
| `DATABASE_URL` | Строка подключения к подготовленной PostgreSQL |
| `JWT_SECRET` | Секрет подписи и проверки JWT |
| `APP_EMAIL`, `APP_PASSWORD` | Учётные данные владельца |
| `VIEWER_EMAIL`, `VIEWER_PASSWORD` | Необязательная пара для доступа только на чтение |
| `CORS_ORIGIN` | Разрешённый origin браузерного клиента; добавляется вручную, в `.env.example` отсутствует |
| `PORT` | Есть в шаблоне, но код её не использует: API всегда слушает `0.0.0.0:3002` |
| `API_URL` | Есть в шаблоне, но backend её не использует |

Backend загружает `.env` из текущего рабочего каталога. Корневая команда `npm run backend` и запуск через `--prefix apps/backend` обеспечивают нужный каталог.

Пароли сравниваются с настроенными значениями окружения; регистрации пользователей и таблицы аккаунтов этот сценарий не предусматривает. JWT выдаётся на 90 дней. Не используйте примерные пароли в опубликованном окружении.

### Мобильный клиент: `apps/mobile/.env`

```dotenv
EXPO_PUBLIC_API_URL=http://192.168.1.10:3002
```

Укажите **адрес сервера без `/api`**: префикс уже включён в пути общего клиента.

| Где запущено приложение | Пример адреса API |
| --- | --- |
| Физический телефон в одной сети с компьютером | `http://<LAN-IP-компьютера>:3002` |
| Android Emulator из Android Studio | `http://10.0.2.2:3002` |
| Android через USB с `adb reverse tcp:3002 tcp:3002` | `http://127.0.0.1:3002` |
| iOS Simulator на компьютере с API | `http://localhost:3002` |

На физическом телефоне `localhost` означает сам телефон. Разрешите входящие соединения на порт 3002 в локальном firewall. После изменения окружения перезапустите Expo; при необходимости очистите Metro-кэш.

`APP_ENV=production` меняет имя Expo-приложения на `Emour` и идентификатор на `com.example.myexpoapp`; по умолчанию используются `Emour Dev` и `com.example.myexpoapp.dev`. Это настройка приложения, а не переключатель production-подписи. После смены нативных параметров требуется обновление нативного проекта/сборки.

В Expo-конфигурации также читается `EXPO_PUBLIC_AI_API_URL`, но рабочий AI-сценарий клиентами не реализован; для запуска она не требуется.

### Веб-клиент

Без `VITE_API_URL` браузер отправляет запросы на свой origin, а Vite dev-сервер проксирует `/api` на `http://localhost:3002`.

Для прямого подключения создайте `apps/web/.env.local`:

```dotenv
VITE_API_URL=http://localhost:3002
```

В этом случае браузер обращается к API напрямую, и `CORS_ORIGIN` backend должен совпадать с origin веб-клиента. `VITE_API_URL` в клиентском коде встраивается **при сборке**, а не читается браузером из окружения сервера.

Для изменения только цели dev-прокси задавайте переменную процессу Vite: конфигурация прокси читает `process.env.VITE_API_URL`, а не явно загруженный `.env`.

**Не помещайте секреты в `EXPO_PUBLIC_*` и `VITE_*`: эти значения доступны клиенту.**

## База данных

Пул подключений находится в [`apps/backend/src/db.ts`](apps/backend/src/db.ts). Запросы выполняются напрямую из файлов [`routes`](apps/backend/src/routes); ORM и команды автоматического применения миграций нет.

**В репозитории отсутствует исходная миграция создания таблиц.** Для чистой установки необходима базовая схема из существующего окружения или отдельный проверенный SQL создания таблиц. Одного создания пустой базы недостаточно; имеющиеся миграции не являются полным bootstrap.

Серверные запросы используют следующие столбцы:

| Таблица | Столбцы |
| --- | --- |
| `feelings` | `id`, `feeling_type`, `score`, `created_at_server`, `created_at_client`, `client_timezone`, `day_part` |
| `symptoms` | `id`, `symptom_type`, `created_at_server`, `created_at_client`, `client_timezone`, `day_part` |
| `notes` | `id`, `title`, `text`, `emotion`, `created_at_server`, `created_at_client`, `client_timezone` |
| `meds` | `id`, `name`, `dosage`, `times`, `days`, `enabled`, `created_at_server`, `created_at_client`, `client_timezone` |

Этот перечень помогает проверить существующую схему, но не заменяет DDL с типами, ограничениями и значениями по умолчанию.

Доступные изменения схемы, в порядке применения:

1. [`002_notes_emotion.sql`](apps/backend/migrations/002_notes_emotion.sql) — добавляет эмоцию заметки.
2. [`003_notes_created_at_client_type.sql`](apps/backend/migrations/003_notes_created_at_client_type.sql) — пересоздаёт `created_at_client` как `timestamptz`.

> **Миграция 003 уничтожает прежние значения `notes.created_at_client`**, заменяя их текущим временем. До применения нужны резервная копия, проверка состояния схемы и осознанное решение о допустимости потери дат. Не запускайте её повторно на актуальной БД.

Только для заранее подготовленной базовой схемы, ещё не получившей эти изменения, после проверки и резервного копирования:

```sh
psql "postgresql://emour:replace-me@localhost:5432/emour" -v ON_ERROR_STOP=1 -f apps/backend/migrations/002_notes_emotion.sql
psql "postgresql://emour:replace-me@localhost:5432/emour" -v ON_ERROR_STOP=1 -f apps/backend/migrations/003_notes_created_at_client_type.sql
```

Команды используют явно переданную строку подключения: `psql` сам не загружает backend `.env`.

## Запуск в разработке

Откройте отдельный терминал для каждого нужного процесса.

### API

```sh
npm run backend
```

API доступен на `http://localhost:3002`. Проверка процесса:

```sh
curl http://localhost:3002/
```

Ожидаемый ответ: `{"status":"ok"}`. В Windows PowerShell при конфликте с алиасом используйте `curl.exe`.

Этот endpoint **не проверяет PostgreSQL**: доступность данных нужно проверять отдельным авторизованным запросом.

### Отдельный веб-клиент

```sh
npm run web
```

Откройте адрес, напечатанный Vite; обычно это `http://localhost:5173`. Войдите с `APP_EMAIL`/`APP_PASSWORD` либо viewer-парой.

### Мобильное приложение

```sh
npm run mobile
```

Для установки и запуска Android development-сборки:

```sh
npm run android --prefix apps/mobile
```

Для iOS на macOS:

```sh
npm run ios --prefix apps/mobile
```

Проверять нативные уведомления следует в собственной сборке на устройстве, с выданным разрешением на уведомления; Expo Go не заменяет проверку всех используемых нативных возможностей.

Для Android через USB в корне есть команда с буквальным именем `atach`:

```sh
npm run atach
adb reverse tcp:3002 tcp:3002
```

`atach` перезапускает ADB, выводит устройства и пробрасывает **только Metro 8081**. Для API нужен дополнительный проброс 3002 выше. С таким пробросом в мобильном `.env` можно использовать `http://127.0.0.1:3002`.

В мобильном пакете также есть `npm run web --prefix apps/mobile` для Expo Web. Это **не** отдельный Vite-клиент; нативные SecureStore/уведомления требуют отдельной проверки совместимости с браузером.

## Обновление общего пакета

Приложения зависят от `file:../../packages/core/emour-core-1.0.0.tgz`, **не от живого каталога исходников**. Изменения в `packages/core/src` сами не распространяются на приложения.

После изменения типов или API-клиента:

```sh
npm run build:core
npm run install:core
```

Перезапустите процессы приложений. Закоммитьте изменения исходников и затронутых lock-файлов; `dist` и `.tgz` — локальные артефакты, в Git не добавляются.

При изменении версии core нужно согласованно обновить имя архива в корневых скриптах, зависимостях приложений и lock-файлах: сейчас версия `1.0.0` прописана явно.

## HTTP API

Базовый адрес разработки: `http://localhost:3002`. JSON-тела передаются с `Content-Type: application/json`. Общий Axios-клиент имеет таймаут 10 секунд.

### Авторизация

```http
POST /api/auth/login
Content-Type: application/json

{"email":"owner@example.com","password":"your-password"}
```

Успешный ответ:

```json
{
  "data": {
    "token": "<JWT>",
    "role": "owner"
  }
}
```

Для всех групп данных требуется заголовок:

```http
Authorization: Bearer <JWT>
```

Мобильный клиент хранит токен и роль в SecureStore, веб-клиент — токен в `localStorage`. При истечении токена нужен повторный вход; refresh endpoint отсутствует.

### Маршруты

Все маршруты ниже, кроме `GET /` и login, требуют авторизации. Для viewer разрешены только GET-запросы.

| Метод | Путь | Действие / JSON-тело |
| --- | --- | --- |
| `GET` | `/` | Публичная проверка процесса: `{"status":"ok"}` |
| `POST` | `/api/auth/login` | Вход: `email`, `password` |
| `GET` | `/api/feelings/all` | Все оценки самочувствия |
| `POST` | `/api/feelings` | `feelingType`, `score`, `createdAtClient`, `clientTimezone` |
| `GET` | `/api/symptoms/all` | Все записи симптомов |
| `POST` | `/api/symptoms` | Непустой массив `symptoms`, `createdAtClient`, `clientTimezone` |
| `GET` | `/api/notes/all` | Все заметки |
| `GET` | `/api/notes/:noteId` | Одна заметка |
| `POST` | `/api/notes` | `title`, `emotion`, `createdAtClient`, `clientTimezone`, необязательный `text` |
| `PATCH` | `/api/notes/:noteId` | Те же поля, что при создании; не частичное изменение |
| `DELETE` | `/api/notes/:noteId` | Удалить заметку |
| `GET` | `/api/meds/all` | Все лекарства |
| `POST` | `/api/meds` | `name`, непустой массив `times`, `days`, `createdAtClient`, `clientTimezone`, необязательный `dosage` |
| `PATCH` | `/api/meds/:medId/enabled` | Включение/выключение: `{"enabled":true}` |
| `DELETE` | `/api/meds/:medId` | Удалить лекарство |

Контракты и допустимые значения описаны в [`packages/core/src/types`](packages/core/src/types):

- `feelingType`: `mood`, `anxiety`, `energy`; интерфейсы используют оценки 1–5, но сервер проверяет только числовой тип оценки.
- `emotion`: `joy`, `calm`, `gratitude`, `sadness`, `anxiety`, `anger`, `fatigue`, `fear`.
- `createdAtClient`: полная дата/время ISO 8601; `clientTimezone`: часовой пояс клиента.
- `times`: массив строк времени, например `["08:00","20:00"]`.
- `days`: номера дней **1 = воскресенье, 2 = понедельник, …, 7 = суббота**; пустой/непереданный список сервер заменяет всеми днями недели.
- При изменении заметки без `text` сервер записывает пустую строку; передавайте текст, который нужно сохранить.

Формат успешных ответов данных — `{"data": ...}`. Создание возвращает HTTP 201, остальные успешные операции — 200. Ответы удаления и переключения лекарства содержат `data.id`.

Формат ошибок обработчика:

```json
{
  "code": "VALIDATION_ERROR",
  "message": "Validation failed",
  "details": {
    "fields": {
      "title": {
        "code": "REQUIRED"
      }
    }
  }
}
```

Сообщения и наличие `details` зависят от ошибки. Основные статусы: 400 — валидация, 401 — нет действительного токена/неверный вход, 403 — запрещённая запись viewer, 404 — запись не найдена, 500 — внутренняя ошибка.

Пагинации, поиска, удаления оценок/симптомов и изоляции данных по пользователям нет. Клиентская функция `apiRegister` существует в core, но серверного `/api/auth/register` нет.

## Сборка и размещение

### Backend

```sh
npm run build --prefix apps/backend
npm run start --prefix apps/backend
```

Запуск использует `dist/index.js`; окружение и доступ к PostgreSQL нужны и в production. Порт остаётся 3002.

Поставляемый [`ecosystem.config.js`](apps/backend/ecosystem.config.js) указывает на `dist/server.js`, что не соответствует entrypoint сборки. Не используйте этот PM2-конфиг без исправления пути и рабочего каталога. Для проверки собранного сервера используйте штатный `npm run start --prefix apps/backend`.

### Веб

```sh
npm run build --prefix apps/web
npm run preview --prefix apps/web
```

Результат: `apps/web/dist/`. Для размещения нужен статический сервер с fallback на `index.html` для React Router.

Dev-прокси Vite **не входит в production-сборку**. Либо настройте reverse proxy `/api` на backend при одном origin, либо задайте `VITE_API_URL` перед сборкой и настройте CORS на API. `vite preview` — средство локального просмотра, не production-сервер.

### Android и EAS

Для проверки текущего нативного Android-проекта без корневого npm lifecycle:

```powershell
cd apps/mobile/android
.\gradlew.bat assembleRelease
```

На macOS/Linux используется `./gradlew assembleRelease` из того же каталога. APK находится под `apps/mobile/android/app/build/outputs/apk/release/`.

**Текущий Gradle release использует debug-подпись**, а нативный `applicationId` — `com.example.myexpoapp.dev`. Такой артефакт не является готовым магазинным релизом. Для публикации нужны отдельный release keystore, настройка подписи и согласованные production-идентификаторы.

[`eas.json`](apps/mobile/eas.json) содержит Android-профили:

- `preview` — APK;
- `production` — Android App Bundle.

Мобильный `npm run build` автоматически выполняет мобильный `prebuild`, затем вызывает `eas build --platform android --profile preview --local`. EAS CLI не включён в зависимости. Локальная EAS-сборка не поддерживается на Windows нативно; используйте поддерживаемое Linux/macOS-окружение либо облачную EAS-сборку после настройки проекта. Для профиля production задавайте `APP_ENV=production` явно: само имя EAS-профиля не устанавливает эту переменную.

Для iOS предусмотрены Expo-конфигурация и команда локального запуска, но отдельных iOS-профилей EAS в проекте нет.

## Проверки

Основные доступные проверки из корня:

```sh
npm run build:core
npm run build --prefix apps/backend
npm run build --prefix apps/web
npm run typecheck --prefix apps/mobile
```

Общего `test`-скрипта и отдельного набора автотестов в репозитории нет. Успешная компиляция не проверяет схему PostgreSQL, доступ с телефона и доставку уведомлений.

Ручная проверка после настройки БД:

1. Запустить API, убедиться в ответе `GET /`.
2. Выполнить вход; проверить, что запрос без токена к `/api/notes/all` получает 401.
3. Под владельцем создать запись самочувствия, симптом, заметку и лекарство; проверить отображение после перезапуска клиента.
4. Под viewer проверить чтение и отказ записи с 403.
5. На устройстве разрешить уведомления, запланировать ближайший приём и проверить уведомление и отметку приёма.

## Git и локальные файлы

Корневой [`.gitignore`](.gitignore) исключает зависимости, логи, TypeScript/сборочные артефакты, архивы `npm pack`, локальные `.env`, Expo/Metro-кэши, нативные сборки и локальные настройки, signing/EAS credentials, файлы ОС и ярлыки.

В Git должны оставаться:

- исходники, ресурсы, SQL-миграции и конфигурация приложений;
- `package-lock.json` каждого пакета;
- `.env.example` и `.env.*.example` без настоящих секретов;
- нативные Android/iOS-исходники и Gradle wrapper, включая `gradle-wrapper.jar`;
- общий Android `debug.keystore`, используемый текущей development-конфигурацией, **не** production-ключ.

Не исключайте целиком `android/` или `ios/`: в текущем репозитории Android-проект уже версионируется. Для него дополнительно действует [`apps/mobile/android/.gitignore`](apps/mobile/android/.gitignore).

Правило `.gitignore` не прекращает отслеживание ранее добавленного файла. В Git уже есть `apps/mobile/android/.kotlin/sessions/kotlin-compiler-7603744367452032308.salive` — локальный файл Kotlin; новые файлы `.kotlin` игнорируются, но этот потребует отдельного удаления из индекса. Это не сделано автоматически, чтобы не менять состав отслеживаемых файлов в рамках документации.

Проверить конкретный путь, в том числе уже отслеживаемый:

```sh
git check-ignore --no-index -v -- apps/mobile/android/.kotlin/sessions/check.salive
```

Если секрет уже попал в историю, добавления правила недостаточно: секрет нужно отозвать/сменить и отдельно решить вопрос очистки истории.

## Известные ограничения и диагностика

| Симптом | Что проверить |
| --- | --- |
| Установка сообщает об отсутствующем `emour-core-1.0.0.tgz` | Сначала установить зависимости core и выполнить `npm run build:core` |
| Изменения core не видны клиенту | Перепаковать core, выполнить `npm run install:core`, перезапустить клиент |
| API отвечает на `/`, но запросы данных падают | Проверить `DATABASE_URL`, доступность БД и полную схему; root не проверяет БД |
| Изменение `PORT` не действует | Порт 3002 задан в коде; переменная пока не используется |
| Телефон не видит API | Проверить LAN IP/адрес эмулятора, firewall, сеть и USB reverse порта 3002 |
| В браузере ошибка CORS | Проверить origin веб-клиента и `CORS_ORIGIN`; для локального Vite можно оставить same-origin dev-прокси |
| После выкладки `/api` возвращает 404 | Настроить production reverse proxy или пересобрать клиент с `VITE_API_URL` |
| Прямое открытие веб-маршрута даёт 404 | Настроить SPA fallback на `index.html` |
| Viewer видит кнопку, но запись запрещена | Сервер правильно отклоняет запись; веб-клиент не скрывает действия по роли |
| Регистрация возвращает 404 | Сервер поддерживает только вход с данными из окружения |
| Не приходят мобильные уведомления | Проверить нативную сборку, разрешение уведомлений, активность лекарства и расписание; в веб-клиенте уведомлений нет |
| Expo использует старый API URL | Перезапустить из `apps/mobile` с `npx expo start --clear` |
| PM2 не находит entrypoint | В поставляемом конфиге указан `dist/server.js` вместо `dist/index.js` |

Для опубликованного окружения необходимы HTTPS, безопасное хранение серверных секретов, резервные копии БД и production-подпись приложения. Медицинские и личные записи чувствительны: учитывайте общий доступ к данным обеих ролей и отсутствие многопользовательской изоляции.
